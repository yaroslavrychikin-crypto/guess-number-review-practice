## Часть 3. Лишние файлы

В ветке автора были найдены следующие лишние файлы и папки:

1. **Папка `__pycache__`**
- *Почему её не должно быть:* Это автоматически сгенерированная папка с байт-кодом Python. Она весит лишнее место, создаётся заново на каждом компьютере при запуске и только замусоривает историю коммитов. Её необходимо добавить в файл .gitignore.
2. **Файл `notes.txt`**
- *Почему его не должно быть:* Это личные рабочие заметки разработчика. В финальном репозитории проекта не должно быть черновых текстовых файлов, не относящихся к коду игры.
3. **Файл `opisanie.md`**
- *Почему его не должно быть:* Дублирующий файл документации с транслитом в названии. Вся основная информация о проекте должна находиться в едином стандартном файле README.md.
**Рекомендация автору:** Удалить эти файлы из репозитория и настроить корректный файл .gitignore, чтобы временные файлы Python больше не попадали в коммиты.

## часть 6. Этика обратной связи

### 5 правил этичной обратной связи при Code Review:
1. **Критикуй код, а не автора:** Оценивай качество написанных строк, алгоритмы и архитектуру, не переходя на личности и не оценивая умственные способности разработчика.
2. **Будь конкретен:** Всегда указывай точное имя файла, номер проблемной строки и суть возникшей ошибки вместо общих размытых фраз вроде "тут всё плохо".
3. **Объясняй причину (почему, а не только что):** Мало просто сказать "переделай". Важно объяснить, к каким последствиям приведет текущий код (например: вызовет падение программы, замедлит работу, усложнит чтение).
4. **Предлагай готовое решение или помощь:** Если критикуешь чужую реализацию, покажи короткий пример правильного кода или вежливо спроси, нужна ли подсказка по исправлению.
5. **Хвали то, что сделано хорошо:** Обязательно найди в ревью хотя бы один позитивный момент (красивое решение, чистый синтаксис, соблюдение ТЗ) и отметь его, чтобы поддержать мотивацию автора.
